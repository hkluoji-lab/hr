# Agent Note: 从 Web 工作台删除已注册账号

Status: implemented

[English](2026-09-12-web-account-deletion.md) | 中文

## Problem

成员制给了 owner 角色管理能力，却没有移除账号的手段。名册列出的是绑定，而一行只在授予之后才存在，因此从未绑定岗位的账号——注册时打错的号、用完的测试号——在任何表面都不可见；表面唯一提供的移除是解绑，而解绑会留下账号行及其凭据。移除这类账号只能停掉部署、手工编辑 `web_login.json`。

## Decision

**`dsh-web-login` 在 accounts 表上新增两条 owner 专属路由。** `GET /team/accounts` 返回 `{ok, owner, accounts}`，按注册时间排序列出全部已注册账号（手机号、掩码显示名、注册时间与最近登录时间）——唯一能触及无绑定账号的列表。`DELETE /team/accounts/:phone` 删除一个账号及其凭据与角色绑定，返回 204。它拒绝 owner 本人的手机号（403）：所有权派生自最早注册的账号，删除 owner 会把全部管理路由交给下一个注册的账号。手机号非法返回 400 `bad-phone`，账号不存在返回 400 `no-account`，非 owner 403，未登录 401。三次删除按凭据 → 绑定 → 账号排序，因此在两次写之间读取的并发读者看到的是「绑定但无账号」，而不是「账号尚存而绑定已被删」。

**客户端在名册旁列出账号。** `loadMembers()` 用同一 fetcher 读两条路由，一个 `Promise.all`、一个状态，`members` 快照新增 `owner` 与 `accounts`。账号列表不重复已授予角色，因此页面按手机号 join 两个列表。owner 本人的行渲染提示而非删除控件，与宿主的拒绝保持一致而不是依赖它；删除被拒时在页面的 alert 里显示宿主消息。

**路由挂在 accounts 表上，不新增表、不升版本。** 所有权本就派生自该表，凭据与绑定都是它的依赖者；删除它们共同依赖的那一行，正是这两张表缺失的操作。

## Alternatives considered

**扩展 `DELETE /team/members/:phone`，在没有绑定时改删账号。** 否决：同一条路由会依隐藏状态表示两种不同的删除，而它的 204 无从说明发生的是哪一种。

**允许 owner 删除自己并把所有权移交给下一个账号。** 否决：一次普通删除就会触发对全部管理路由的不可逆、静默移交。改为拒绝 owner 本机号。

**软删除或停用标志。** 否决：账号行是手机号键、凭据是散列，两者都不带值得保留的历史，而每个读都要过滤该标志。被移除的测试号应当立刻能重新注册。

## Consequences

删除账号会一并丢掉其凭据与绑定，因此该手机号可重新注册，且在再次被授予之前不持任何角色。任何删除都不会移动所有权，因为 owner 无法删除自己。仍持有有效登录 cookie 的浏览器保有其 cookie：`/auth/status` 会以 `authenticated: true` 与该 subject 作答，但既无 `displayName` 也无 `roles`，因为它读取的账号行与绑定都已不在。注册时间与最近登录时间只在账号列表上对 owner 暴露。

## Testing

web-login 测试端到端覆盖两条路由：owner 守卫链（未登录 401、非 owner 403、owner 自身拒绝）、按注册顺序的列表（含无绑定账号）、方法守卫、`bad-phone` 与 `no-account`，以及级联——删除后名册为空、密码登录返回 `no-credential`、被释放的手机号可重新注册。信任栅栏与销毁测试把这两条路由与既有路由并列枚举。客户端测试覆盖双读快照（一个状态、两条路由均被记录）、删除往返，以及页面的账号区：从名册 join 来的角色、未绑定提示、无删除控件的 owner 行、成功删除，以及渲染在 alert 中的宿主拒绝。
